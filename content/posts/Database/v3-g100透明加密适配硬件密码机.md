## 1. 透明加密适配硬件密码机

依托PSU3实现的透明加密模块，在此基础上适配BJCA密码机，主要是使用BJCA的密码机加解密以及密钥管理能力实现更安全的透明加密。很多用户都会有这种诉求，通常不会只依赖数据库自带的透明加密特性。

### 1.1 功能简述

语法上与软加密使用方式相同，只是在建立密钥的通过option进行区分：
```python
create encryption key k1 with(source=hsm);    ##hsm（Hardwire-Security-Module)表示使用硬件设备进行密钥创建，以后使用此密钥的策略都走硬件路径；软加密这里是local，意为本地加解密。
create encryption policy p1 key k1 algorithm sm4_ctr mac_algorithm hmac_sm3;
create table t1(a text) secured by(encrypt_policy='p1');
insert into t1 values('tde_plain');
select a from t1;
```

这里需要说明的是，一个集群中只能部署一种类型的密钥，如果key的source指定为local，就无法再创建hsm的硬件加密密钥，这样处理的原因是，如果混用不同来源的密钥，很容易造成一些未知的错误，导致加解密状态混乱，因此现在的设计时，严格限制密钥的单一来源；如上所述，就会带来一个存量迁移的路径，例如之前使用软加密，现在向前一到硬件加密去。这个诉求也很常见，后面会讲到具体的做法。

如何限制单一密钥来源？后面的章节会结合代码树分析，主要是在实例启动的时候去做限制。

友商关于这个模块的实现，在内核中大致的思路是类似的：
- 达梦、金仓：内核通过调用统一的接口，来实现对硬件加密设备的连接，从而不必关心不同设备所带来的差异，具体的架构类似于：
```bash
--------------     可能有接口差异  ------------   提供统一的API      ------------
硬件加密机            -------->      封装库整合   -------------->        内核
--------------                   ------------                    ------------ 
```

但是对于封装库，达梦和金仓都选择了一个自定义的头文件类型，由用户去自行做三方硬件设备的适配工作，这样的好处是研发连适配具体的哪个硬件都不用关心了，而且也不需要关心未来第三方的更新等等，缺点就是把复杂度转移给了用户，从体验上感觉不好。

本次硬件适配的方案时由内核以插件的形式自带三方封装库，这样的好处是用户只需要按照指定步骤进行配置即可，不用自己创建头文件
