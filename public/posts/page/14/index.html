1 逻辑复制性能优化 1.1 功能简述 原理： 假设，发布端执行INSERT INTO t1 VALUES(1,'data1')，更改1行数据，产生1条wal日志。逻辑复制功能将读取这条wal，解码并生成1条message，将message发送至订阅端。订阅端应用这条message，等价于重新执行INSERT INTO t1 VALUES(1,'data1')。 问题： 308.1 psu1以及之前版本，逻辑复制性能较低。以tpcc场景为例，40w tmpc时，发布端产生wal日志速度约100m/s，订阅端的复制速度约10+m/s。 客户： 滚动升级场景中，备机停机升级，主机持续执行业务，备机升级后使用逻辑复制追赶主机数据。长存客户场景，主机产生wal日志速度约40-50m/s，旧版本逻辑复制速度10+m/s，由于逻辑复制速度太慢，备机无法追赶主机，最终导致升级失败。 优化 本需求设计与实现并行逻辑复制机制，大幅提高逻辑复制速度，在上述场景中，订阅端速度可达到70-90m/s。并行逻辑复制分为3个关键子机制： 发布端多线程并行解码 发布端与订阅端流复制传输协议 订阅端多线程并行应用 1.2 实现方案 本章分3个章节，分别介绍3个关键子机制。 1.2.1 发布端并行解码机制 在旧版本中，发布端采用串行解码机制，只有1个walsender线程，串行执行：1次读取1条wal日志，解码1条wal生成1条message，缓存或发送message。 旧版本代码中，发布端有实现并行解码的代码，但是，无法直接使用，订阅端只能是工具，不能是数据库实例，且存在大量问题。本需求基于旧版本并行解码，实现权限的并行解码机制。 并行解码机制，将启动多个线程，包括1个reader、多个decoder、1个walsender，它们的功能如下： reader：1次读取1条wal日志，将wal发送给decoder decoder：1次接收1条reader发送的wal，解码生成message，将message发送给walsender walsender：1次接收1条decoder发送的message，将message发送给订阅端 线程架构图如下： lsn 1-10 d1 1 4 collect 阻塞 1 d2 2 5 2 d3 3 6 3 1.2.2 发布端与订阅端流复制协议 一、握手阶段 订阅端与发布端建立连接时，订阅端会根据CRETE SUBSCRIPTION语法设置的参数，生成连接命令，根据连接命令，发布端和订阅端决定采用哪种通信协议，究竟是采用事务复制协议（旧版本）还是流复制协议（新版本）。 事务复制协议（旧版本） 订阅端发送的连接命令如下： START_REPLICATION SLOT "$slot_name" LOGICAL $start_lsn (proto_version '3', publication_names '"$publication_name"') 流复制协议（新版本） 如果CRETE SUBSCRIPTION时，指定worker_number>1，即启用并行逻辑复制机制，将使用新的连接命令，订阅端发送的连接命令如下： START_REPLICATION SLOT "$slot_name" LOGICAL $start_lsn (proto_version '3', publication_names '"$publication_name"'， streaming 'extreme', parallel-decode-num '20', max-recordbuffer-in-memory '100', max-txn-in-memory '100') 上述命令中新增了多个参数： ...

V3-G100透明加密适配硬件密码机

V3-G100透明加密适配硬件密码机 对硬件适配的代码做梳理性总结，同时自己仔细过一遍。 软加密的详细设计请看另一篇文档 1. 透明加密适配硬件密码机 依托PSU3实现的透明加密模块，在此基础上适配BJCA密码机，主要是使用BJCA的密码机加解密以及密钥管理能力实现更安全的透明加密。很多用户都会有这种诉求，通常不会只依赖数据库自带的透明加密特性。 1.1 功能简述 语法上与软加密使用方式相同，只是在建立密钥的通过option进行区分： create encryption key k1 with(source=hsm); ##hsm（Hardwire-Security-Module)表示使用硬件设备进行密钥创建，以后使用此密钥的策略都走硬件路径；软加密这里是local，意为本地加解密。 create encryption policy p1 key k1 algorithm sm4_ctr mac_algorithm hmac_sm3; create table t1(a text) secured by(encrypt_policy='p1'); insert into t1 values('tde_plain'); select a from t1; 这里需要说明的是，一个集群中只能部署一种类型的密钥，如果key的source指定为local，就无法再创建hsm的硬件加密密钥，这样处理的原因是，如果混用不同来源的密钥，很容易造成一些未知的错误，导致加解密状态混乱，因此现在的设计时，严格限制密钥的单一来源；如上所述，就会带来一个存量迁移的路径，例如之前使用软加密，现在向前一到硬件加密去。这个诉求也很常见，后面会讲到具体的做法。 如何限制单一密钥来源？后面的章节会结合代码树分析，主要是在实例启动的时候去做限制。 友商关于这个模块的实现，在内核中大致的思路是类似的： 达梦、金仓：内核通过调用统一的接口，来实现对硬件加密设备的连接，从而不必关心不同设备所带来的差异，具体的架构类似于： -------------- 可能有接口差异 ------------ 提供统一的API ------------ 硬件加密机 --------> 封装库整合 --------------> 内核 -------------- ------------ ------------ 但是对于封装库，达梦和金仓都选择了一个自定义的头文件类型，由用户去自行做三方硬件设备的适配工作，这样的好处是研发连适配具体的哪个硬件都不用关心了，而且也不需要关心未来第三方的更新等等，缺点就是把复杂度转移给了用户，从体验上感觉不好。 本次硬件适配的方案时由内核以插件的形式自带三方封装库，这样的好处是用户只需要按照指定步骤进行配置即可，不用自己创建头文件，缺点就是未来一旦第三方厂商出现更新，或者随着越来越多种类的第三方适配，代码库可能会变的更多更杂，主要原因还是0018标准不够清晰和全面，导致各个厂家在实现的时候，仍然有一定的差异化。 如前所述，使用可以概括为： 密钥在密码机中生成，现阶段使用的是kek类型的密钥，密钥不出密码机，内核只持有加密后的密钥密文； 软硬件路径互斥，集群中只能存在一种类型的加密密钥； 算法集主要以国密算法为主，本次实现使用的是SM4算法，覆盖的模式有CTR/GCM/CBC，同时还支持完整性校验算法HMAC_SM3； 封装库为common_cipher.so，封装库的实现请参考另外的章节； 使用BJCA的密码机服务库libSDF.so； 1.2 实现方案 本节主要通过函数调用树的方式，来介绍具体的实现路径。 【启动阶段】 PostmasterMain. # 校验enable_tde主特性开关 if (enable_tde) tde_hw_register_exit_hook() # 注册进程退出回调，因为在进程关闭时需要同步调用密码机的关闭接口，这里是无条件创建的； if (tde_hw_conf_present() && !tde_key_info_file_exists()) # 这里判断硬件配置文件的存在性，如果存在这个配置文件，就认为需要走硬件路径； if (tde_hw_startup(FATAL)) # 这里就尝试打开密码机设备，FATAL参数说明如果这里执行失败，实例会FATAL掉，这样设计的目的是为了不在异常的前提下提供任何服务，避免出现更严重的问题； if (tde_hw_is_active()) # 这里是有一个static进程级别的变量，标识密码机是否已经处于激活状态，因为密码机状态可能随时变化，采用原子读的方式读取这个变量，如果已经激活，就直接返回，算是一个快路径，除了刚启动，大多数； pthread_mutex_lock(&tde_hw_startup_lock);
